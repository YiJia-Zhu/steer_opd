# 空闲GPU利用率与参数任务保活排查

2026-11-18本轮排查只对GPU0执行了`fix_gpu_util.py 0 --check`及NVML／pmon查询，没有执行GPU0 CUDA修复、kill或reset。GPU0连续10次、约20秒采样均为0%利用率、0 MiB显存、功耗约54–55W；pmon没有计算或图形进程。当前ECC计数为0，NVML recovery action为None。内核日志读取受权限限制，无法据此核实Xid或确认驱动内部根因。

GPU0仍有多个活动进程打开设备文件，包括在GPU2／3工作的参数模型和GPU6／7的训练组件。设备文件句柄不等同于在GPU0执行CUDA计算，不能将这些句柄直接认作应清理的残留计算任务。

`fix_gpu_util.py`的修复分支在确认显存为0且无计算进程后，通过Driver API创建自己的上下文，分配1 MiB、写入／读回／同步，最终释放内存和上下文。它是轻量CUDA自检及状态刷新。若它能解除持续100%利用率现象，仍不能单凭这一点判定驱动根因。上下文自身还会占用额外显存；1 MiB指显式测试块。脚本的无进程检查针对NVML计算进程列表，不是所有设备文件句柄。

同类症状早在2026-11-14的GPU2审计中已有记录，见`audit/easysteer_startup_20261114/gpu2_cleanup_recheck.json`；当时已核实无已知实验进程、无当前用户可见的设备句柄，但显存0且利用率100%。当前证据支持继续排查CUDA上下文退出／驱动遥测状态异常，尚不足以归因到某个具体模型算法或驱动版本缺陷。

本次参数实验持续在GPU2／3推进，700题评分、CPU指标、gzip提交及300题Confirm之间，主搜索组数只在整组提交后更新。GPU0的空闲读数与参数进度应分别观察。

用户随后明确要求CPU阶段保留显卡。为此增加独立参数保活入口，根目录`src/`、`scripts/`、配置与科学数据绑定均保持原值。保活进程在GPU2、3各持有1 MiB测试块及一个CUDA上下文，NVML实测约336 MiB／卡；休眠期间不执行模型或忙循环。参数准入仅忽略经过PID／启动时刻／所有者验证的本任务保活进程，仍拒绝其他计算进程、超额显存及异常100%利用率。实际占用与保活PID保留在准入凭据中，不隐藏真实NVML数据。

当前GPU引擎阶段结束后交接监督器，保留完整提交，再继续原冻结网格。任务成功、失败或保活所有者退出时释放自己的上下文。此方式向遵守空闲GPU检查的任务表明显卡已被使用；它不提供管理员级硬性独占。
