原先约50小时估计的大约八成来自密集完整评测；这不是新的精确ETA。

## 长度为何影响速度

`scripts/profile_figure8_generation.py`使用dev衍生前缀，固定16条请求，每条512个输出token，
temperature0.7/top_p0.95。为固定硬件工作量，诊断设置min_tokens=512/ignore_eos=True；
没有拿它做准确率评测，也没有把其文本写入正式实验。

| 起始前缀长度 | 后64次engine.step中位时间 | 约稳定解码吞吐（16/token步） |
|---:|---:|---:|
| 128 | 5.80 ms | 2757 token/s |
| 8192 | 17.84 ms | 897 token/s |
| 16384 | 30.08 ms | 532 token/s |
| 30000 | 50.45 ms | 317 token/s |

吞吐由16除以step中位时间估算，适用于这段16请求同时decode的窗口；不是整次评测吞吐。
整体用时含长prefill，16K案例还含profiler处理，因此不用整次案例平均值冒充稳定decode速度。
32个被profile的16K decode步骤共有934.41 ms kernel时间，FlashAttention split-KV及combine共约795.40 ms。
正式GPU快照为100% GPU利用率、约89%显存控制器活跃率；KV缓存没占满不能推断GPU空转。

该学生28层、8 KV heads、head_dim128、BF16，每个历史token约112 KiB KV。
接近32K时16条请求的KV约55 GiB。日志显示可缓存550342 token，按32024长度仅支持17.19条满长请求。
全量排队与同时运行480条不同，盲目继续提高评测并发可能产生KV抢占/重算。

## 已排查及低优先项

- 全部请求已经一次入队：每次评测480条，并未在外层分小批等待。
- 没有漏掉已生成的EOS：480条Base结果中，截断回答均不含151643/151645；289条正常结束的末token均为151643。
- 本地Base config/tokenizer_config与本次获取的官方main文件hash相同。这只排除文件差异，不证明当前Base的任务模式最优，也不单独解释为何模型退化。
- prefix cache：Base评测全部prompt合计69488 token，输出6396207 token；输入短、答案很长。prompt缓存不能复用各条不同生成历史的大部分KV，不应优先指望它解决数小时瓶颈。
- chunked prefill主要处理长prompt/混合prefill调度，当前AIME平均prompt仅145 token；收益待测，排在长decode内核之后。
- FlashInfer采样器：采样相关GPU kernel本次仅0.67%；不要与FlashInfer attention后端混淆。
- 编译/额外融合尚有机会，但已有decode CUDA Graph；除attention外仅约15%的kernel时间，不能未经实测承诺大幅加速。
- EasySteer可用于rollout集成；主AIME评测无steer，仅替换steering组件不能直接消除这里的attention成本。

保留科学协议时，后续应优先比较长序列attention后端与KV访问效率，再测生成并发/调度。
重复提前停止、改变长度或采样数属于科学协议变更，本次不实施。减少中间完整评测仍是独立预算选项，
未获得用户选择前保留原日程。
